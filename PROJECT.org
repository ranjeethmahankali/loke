   =DVec::dot= (and the f32 =Vec::dot=) in =src/vec.rs= use =mul_add=. Inside this repo,
   =.cargo/config.toml= sets =target-cpu=native=, so it compiles to an FMA instruction. Crates
   that depend on loke don't get that flag, so =mul_add= falls back to a slower path. Measured
   with a harness outside the repo, the elliptic arc uniform-sampling span walk took 13.9 ns per
   span without the flag, against 6.8 ns with it. Every curve calls =dot=. Options: plain
   multiply-add (=a * b + c=), or =mul_add= only when the =fma= target feature is enabled.

   Questions: How do plain operators compare in performance to the mul_add with cpu=native? How much
   performance are we leaving on the table by worrying about projects that don't compile to native
   CPU? Does branching based on fma feature availability get us the best of both worlds?

  polynomials, and sample points. So maybe provide an 'projector' object that caches this stuff,
  deals with all curve types, and projects points onto the curves.

  Spline projection logic is dimension agnostic. Lines are trivial. Arcs are interesting.

  I can write specialized logic for 2d and 3d arcs. I would need to look at the derivative
  expression for the general dimension agnostic arc, and find all points where the dot product with
  the query point and the tangent is zero. I wonder if I can generalize this. If I can, I should
  compare the performance with the special case logic for 2d and 3d arcs. Maybe the generalization
  is just as fast, and I don't need the specializations? Unlikely in 2d, unsure in 3d, very
  interesting to try.
